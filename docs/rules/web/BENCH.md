# Web Source Audit — бенчмарк и устойчивость (CL-WEB-11)

Измерено 2026-11-12, одна машина, без повторов на других ОС. Это замер, а не гарантия (SLA нет).

**Машина:** AMD Ryzen 7 5800X, Windows 11 Pro, NTFS, `rustc 1.98.0`, `--release` (`lto`, `codegen-units=1`).
**Команда:**
```
cargo test --release --lib web_audit::bench::bench_synthetic_tree -- --ignored --nocapture
JETSCAN_WEB_BENCH_MB=10 cargo test --release --lib web_audit::bench::bench_synthetic_tree -- --ignored --nocapture
```

Дерево генерируется в момент теста во временный каталог (`src/web_audit/bench.rs`, `generate_tree`)
и удаляется после; в репозитории больших файлов нет. Синтетический Next.js-проект: ~10 КБ на файл,
половина — клиентские компоненты (`"use client"`), четверть — `app/**/route.ts` с ключом (сервер,
не должен попадать в находки), четверть — `lib/*.ts`; ключ подложен в каждый 50-й клиентский файл.
Кэш ФС прогрет (первый прогон — генерация). Три прогона, медиана.

| Объём | Файлов | `web source` медиана (min–max) | Ядро `secrets --no-history` медиана (min–max) | Найдено / подложено |
|---|---|---|---|---|
| 10 МБ | 980 | 388 мс (387–647) — 25.8 МБ/с | 382 мс (350–383) — 26.2 МБ/с | 10 / 10 |
| 100 МБ | 9 788 | 3.61 с (3.59–4.72) — 27.7 МБ/с | 3.37 с (3.33–3.41) — 29.6 МБ/с | 98 / 98 |

Вывод: `web source` по скорости в пределах ~7% от ядра на тех же файлах (он прогоняет те же матчеры
ядра плюс токенайзер и свои правила). Время растёт линейно с объёмом (10 → 100 МБ: ×9.3).
Ложных находок по серверным `route.ts` с тем же ключом — 0. Память не измерялась (std-only, без
системных API); по построению файлы читаются по одному, в памяти — текущий файл, его разметка
(1 байт на байт) и находки.

**Бюджеты по умолчанию:** файл 1 МиБ, всего 64 МиБ, 20 000 файлов, глубина 64. В бенчмарке
общий бюджет поднят (4 ГиБ / 1 000 000 файлов), чтобы померить 100 МБ; в обычном запуске такое
дерево дало бы `partial` с причиной «scan budget exhausted», а не «чисто».

## Устойчивость (обычные тесты, `src/web_audit/bench.rs`)

| Тест | Что проверяет |
|---|---|
| `huge_minified_line_is_linear_and_still_scanned` | 900 КБ одной строкой в `public/*.min.js`: ключ в конце найден, колонка точная, фрагмент ≤160 символов |
| `adversarial_line_of_tokens_is_capped_and_reported_partial` | строка из 20 000 ключеподобных токенов: разбор останавливается на `MAX_HITS_PER_FILE` = 200, правило `partial` с путём файла, `completed() = false` |
| `many_sinks_on_one_line_are_capped` | 50 000 `innerHTML=` на строке → `WEB-XSS-003` `partial` |
| `broken_syntax_does_not_panic_and_is_disclosed` | незакрытые строка/шаблон/комментарий/регулярка, мусорные скобки, BOM+CRLF, пустой файл → без паники, limitation о приблизительной разметке |
| `deeply_nested_templates_and_brackets_do_not_overflow` | 50 000 вложенных `` `${ `` и скобок — нет рекурсии, стек не переполняется |
| `deep_directory_nesting_hits_depth_budget` | 70 уровней каталогов → `depth_limited`, правила `partial` |
| `non_utf8_and_utf16_inputs` | невалидный UTF-8 → U+FFFD (1 символ в колонке), ключ после него найден на верной колонке; UTF-16 (NUL-байты) → пропущен как бинарный и посчитан |
| `file_over_size_limit_makes_rules_partial` | файл больше 1 МиБ → `skipped_large`, правила `partial` |
| `small_generated_tree_finds_exactly_the_planted_keys` | ~400 КБ сгенерированного дерева: найдено ровно подложенное, серверные ключи — нет |

Весь набор: 0.85 с в `--release`, 8.1 с в debug (граница «не зависло» в тестах — 20 с на тест;
квадратичный разбор мегабайтной строки занял бы минуты).

## Что исправлено по ходу CL-WEB-11
- Разбор одного срабатывания стоит O(длина строки) (позиция, `jetscan:ignore`, фрагмент). Строка
  с десятками тысяч срабатываний давала бы квадратичное время → лимит 200 срабатываний на правило
  на файл, остаток — честный `partial` с причиной.
- Сопоставление «переменная `.env` ↔ чтения в коде» (WEB-ENV-002) было O(переменные × чтения) →
  индекс по имени.

## Не измерено
Linux/macOS, холодный кэш ФС, сетевые диски, реальные (не синтетические) монорепо на 1 ГБ, память.
